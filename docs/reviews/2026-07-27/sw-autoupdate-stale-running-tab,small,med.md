- description: The SW registration block (lines 28-33) registers `/sw.js` in production and relies on `skipWaiting()` + `clients.claim()` inside the SW for "autoUpdate" behavior. The comment on lines 26-27 claims "no client-side update messaging is needed here." That is incorrect for the running tab: `skipWaiting()` activates the new SW and `clients.claim()` lets it control existing clients, but the *already-loaded* React app keeps running its old hashed JS bundles. The new SW only serves the new bundles on the *next* navigation. So after a daemon update, a paired device that keeps the tab open continues running the old UI indefinitely — it will talk to the new daemon with stale wire types, hit mismatched contract shapes, and show confusing errors (this app uses authenticated WebSocket sync with event replay and ACP wire types mirrored from `src/interfaces/`). The user is never prompted to reload. Fix: listen for `navigator.serviceWorker.addEventListener('controllerchange', ...)` (or use `registration.waiting` + a `updatefound`/`controllerchange` flow) and either call `window.location.reload()` once a new SW activates, or surface a non-blocking "A new version is available — reload" banner. Given the daemon/client contract coupling, auto-reload on `controllerchange` is the safer default.
